# Bot of Culture: public review browser scope

Status: technical scope and design proposal; no production feature, migration, deployment, or command registration performed. Product recommendations marked below are not approvals. Prepared 2026-09-08 (America/New_York).

## Outcome and boundaries

A lightweight, mobile-first, public, read-only browser for reviews already written in Discord. Two durable entry points: a person's global review profile and a server's library of global reviews by its current members, regardless of where those reviews were created. Anyone with a link can view; there is no viewer login. Existing and future reviews are public by default, subject to a global per-user web opt-out and exclusion of any explicitly private reviews.

The library groups by media title and shows individual member reviews. Title search is confirmed for launch. Store names in the bot’s database and search them on the same screen with media filters. The user reports few existing reviews and accepts a modest backfill; this scopes that work and does not authorize running it. Small batches load automatically near the bottom. Filters are All, Movies, TV series, Games, Music (albums/singles, not a new song-review model). Links from authors open their global profiles. Write, edit, delete, co-sign and quote interactions remain in Discord. No web review editor, web account, follows, reactions, leaderboard, recommendations, server directory, global user directory, or cross-server navigation exposing a person's memberships. Visibility settings are the only new write operation, authenticated by Discord slash interaction.

## Recommended architecture and alternatives

**Recommendation:** retain MongoDB and the four review collections, and add a bounded Express web module in the existing Node process for initial scale. Serve a simple responsive HTML/CSS interface plus a same-origin GET API. Reuse the initialized Prisma client and media services through explicit injected dependencies; route handlers must call new public-read policy/query services, not Discord embed helpers. No new React/Next.js app, OAuth service or database platform is necessary. A static design artifact is not a deployed site.

Alternatives: a separate web process in the same repository gives better failure isolation and independent scaling but requires a persisted membership projection and coordination for privacy freshness; reserve it for measured traffic or an operator's isolation requirement. Static exported review JSON is operationally simple but makes opt-out invalidation and current membership unreliable; reject for this release.

One-process tradeoff: web requests share bot resources. Bound API concurrency, query execution time, rate limits and provider requests; publish through HTTPS reverse proxy with limited ingress. Startup must not mark server-library routes ready until gateway/member synchronization completes. Database or privacy-read failures fail closed. Use separate read service interfaces so moving to a second process later does not change public contracts.

## Proposed data contract

Keep native collection names and provider IDs. At the public boundary normalize a review into type, id, mediaId, userId, displayName, avatarUrl?, score, comment?, createdAt, updatedAt?, hoursPlayed?, replayability?, sharing?, reviewedInAnotherServer. Raw guild/origin IDs and private flags must not leave this boundary. Discord IDs are strings, never JavaScript numbers.

| Change | Meaning |
| --- | --- |
| Unique `(mediaId,userId)` in each media collection | One canonical current review per person/title globally, after resolving legacy duplicates. No additional unified write collection. |
| `originGuildId: String?` | Immutable creation source for this canonical record; set from interaction.guildId on creation, including co-sign/quote. Preserve on edits in other servers. Null means unknown/unrecorded, not proof of another server. |
| `originSource: String?` | Optional audit classification such as observed_creation or legacy_guild; not a UI field. Helps distinguish reconstructed provenance. |
| `updatedAt: DateTime?` | Last meaningful edit timestamp, explicitly set when an existing review’s score, comment, hoursPlayed, replayability or sharing/quote content changes. Leave null/missing on creation and for unknown legacy edit history. No-op saves, profile refreshes, visibility changes and migration do not set it. This field never affects ordering. |
| `isPrivate` if global branch is retained | Separate review-level restriction. Web excludes true everywhere, even when viewed in its original guild. Normalize verified legacy missing values before relying on filters. |
| `UserWebPreference` | Unique userId; visibility `PUBLIC` or `HIDDEN`, changedAt. Missing preference means PUBLIC. Explicit invalid/unreadable preference data must not default open. No user backfill needed. |
| `MediaTitle` (launch search) | New minimal title lookup: type, mediaId, title, normalizedTitle, fetchedAt, plus Mongo _id; unique type/mediaId. Retain last-known names. No title fields are added to review documents; no artwork/year/cache platform is required. Neither this collection nor search exists on master today. |

Creation origin is not last broadcast location or the original author's guild when quoting. 'Reviewed in another server' appears only on server pages when reliable origin is known and differs from the viewed server. Same-server and unknown origins remain unmarked. Do not display foreign server names, links, or inferred membership. For pre-global guild-scoped records, guildId is usable provenance for the retained record. If global code already ran, inspect migration/runtime history and archived originals; never invent missing history.

User confirmed selecting the most recent canonical record. With available evidence, use the newest created record per user/type/media, deterministic tie-break by ObjectId descending. User is open to archiving displaced records; the proposed storage below remains subject to review. Conflicting scores/comments appear in a dry-run report for review. This is a canonicalization decision, not a claim about most recently edited content.

### Visibility policy (mandatory on every public path)

1. Review author is web-public: explicit PUBLIC or no preference document.
2. Review is not explicitly private and legacy privacy state has been normalized/validated.
3. For server pages, author is a verified current member of that server and bot still belongs to the server.
4. Apply these before ordering, grouping, counts, paging and serialization. Do not leak hidden activity through empty groups, totals, timestamps, score aggregates or metadata previews.
5. Copied quote source requires its own check: source author must be public, source review must still exist and be non-private; on server pages also require source current membership for source content/attribution. Otherwise suppress copied name, ID, text and source links and use 'Source review unavailable'. Retain the visible quoting user's own words/score. A co-signer's adopted score is their review; no source excerpt is necessary. Legacy links identify user/type/media, not exact historical review version, so uncertain sources are suppressed.
6. Serialize only allowlisted fields; never ship hidden data in HTML, JSON, embedded state, logs or error messages for browser-side filtering. Render user text as escaped plain text initially; do not execute raw HTML or expose raw Discord mentions as profile data.

Preference updates use interaction.user.id exclusively, never a user option supplied to the setting. `/reviews visibility` without a value reports the caller's setting ephemerally; `public`/`hidden` updates it atomically and acknowledges only after storage succeeds. Setting survives bot/server departures and applies to all profile/library paths and all old/new reviews. It does not edit/delete Discord messages or change ordinary Discord visibility. Existing and future private review rules remain separate.

Do not cache review HTML/API responses or preference decisions in MVP: `Cache-Control: no-store`, no shared CDN cache, no service-worker review cache. Read preference state for each response. Revalidate before final serialization if a request does long provider work. The viewer keeps loaded reviews in place with no automatic refetch on a timer, focus, or tab visibility. Explicit reload, search/filter changes, and navigation start a new result set; pagination continues the existing asOf cutoff and still checks current privacy. A hidden/not-available response clears the affected view and offers manual retry. A completed opt-out prevents subsequent authorized responses; it cannot retract screenshots or bytes already received. Already loaded reviews can remain on an open page until the reader reloads or makes a request that invalidates the view. Do not claim retroactive deletion.

## Current-member semantics

`guild.members.cache` is not an authoritative roster with the current Guilds-only intent. Recommended implementation enables GuildMembers in code and the Discord Developer Portal (approval may be required), obtains a complete paginated/chunked member snapshot at readiness, then applies member add/remove events. No message-content intent or role-based public-viewer authorization is needed. Discord documents the [privileged intent requirement](https://docs.discord.com/developers/events/gateway) and [member listing endpoint](https://docs.discord.com/developers/resources/guild).

Use an in-memory MembershipService for one process: complete snapshots, generation/version, synchronizedAt, ready/unavailable state; no permanent roster dump exposed publicly. Reconcile every five minutes, coalesce requests, respect Discord rate limits. Apply leave immediately when event received. On gateway disconnect, nonresumable gap, partial snapshot, stale snapshot >5 minutes, or unknown/bot-removed guild, suspend that server's content. Rebuild snapshots atomically and replay buffered events; never treat an incomplete cache as an empty but valid library. Profile pages can continue independently.

Operational contract: current means latest complete synchronized membership plus received gateway events, with periodic reconciliation bounded to five minutes. An absolute instantaneous guarantee is not possible over a remote API. Recommended UI has a subtle 'Members synced …' status; during failure show 'Server library temporarily unavailable. Try again shortly.' Do not fall back to guildId-based review origin filtering. If privileged intent is unavailable, deciding between slower verified per-reviewer REST checks and postponing server view is an execution gate; silently shipping an origin-only server library violates the product requirement.

## Star ratings and server-title summaries

Verified composer scale: `src/commands/utils/choices.ts` defines values 1, 2, 3, 4, 5 for movies/TV, games and music; Prisma stores score Int. There are no half-star individual inputs. `utils/index.ts:475` displays filled star emoji plus unfilled placeholders and indexes integer choice descriptions. `buttons/select.ts:218` currently floors averages before the Discord overview uses them. Reuse the 1–5 semantics, not the integer-only formatter/floored-average helper for fractional web averages. No Discord composer behavior changes are in this scope.

Individual reviews show five visual star positions: score whole filled stars, remaining positions outlined/unfilled. Use a warm readable star fill (#f0b232 on dark surfaces) and muted outlines; do not replace stars with a numeric-only rating. The accessible label is, for example, '4 out of 5 stars'. No partial individual stars or rating input controls are added. Treat invalid historical scores as data-quality exceptions in the audit; never silently clamp or fabricate a valid rating.

On SERVER title groups, place a compact five-star average and review count at the right of the title header, sharing its text baseline. Remove the latest-review date from that header; individual review dates remain. Keep the stars in a stable summary column and right-align the count to the content edge. On narrow server layouts, wrap this summary as one unit below the title, preserving stars-before-count and avoiding long-title overlap. This does not add a community summary to personal profiles. Aggregate once over the full eligible review set for that type/media: current members, web-public authors, non-private reviews, current query/media filter and asOf creation cutoff. Compute count and sum/average before limiting title previews or member-review pages. Each canonical review contributes once, including an eligible co-sign/quote as that member’s own score; do not separately count copied source text or multiply by shares. Do not use all-bot/global provider scores or average only the displayed first three. Profiles show only that person’s own stars; no community average/count is added there.

API `averageScore` is the unrounded arithmetic mean or null for an empty set; `visibleReviewCount` is the full eligible count. For display, round once to one decimal (ordinary half-up), fill that many star units left to right using clipped vector shapes, and expose the same rounded numeric value in accessible text. Example 3.5 uses three full stars and half the fourth; 3.7 uses 70% of the fourth, not a half-star snap. Accessible summary: 'Average 3.5 out of 5 stars, 2 reviews'; an optional hover/focus hint may show the decimal without adding another permanent column. Do not claim hundredths of precision. Star graphics are decorative beneath one accessible label. Counts use correct singular/plural. No stored aggregate or new aggregate collection is necessary.

If no eligible reviews remain, omit the title group from listings/search; a direct title expansion responds with empty reviews, count 0 and averageScore null, rendered as 'No reviews' without zero-star/NaN output or hidden-title metadata. Hidden/opted-out/nonmember reviewers must not affect title presence, latestReviewCreatedAt, average, count or search coverage. If invalid scores are discovered, resolve them before rollout or fail that title summary safely rather than quietly producing a count/average inconsistent with the displayed valid set.

Score edits update that title’s average and the author’s star row, preserving createdAt ordering. On the next user-initiated reload, replace group summary and review content together; expansion responses include the same full-set average/count so the header never substitutes a page-local value. The existing asOf snapshot excludes newly created records until refresh, consistently for list order, aggregate and expansion. Opt-out/member leave invalidates eligibility state and recomputes all fields, rather than patching the average on the client.

Verification: sample movie scores 4 and 3 yield 3.5/2; sample game 5 yields 5.0/1. Four eligible reviews [5,4,3,2] with only three loaded must report 3.5/4. Hiding the 3-star sample leaves 4.0/1; hiding both removes the group. Score change 3→5 changes 3.5 to 4.5 without moving the group. Test all individual integers 1–5, fractional means 3.25→3.3 and 3.75→3.8, no zero/NaN for empty groups, no effect from nonmembers/private authors, and profile absence of community averages. Test one shared canonical review counts once, full-set consistency across expansion pages, and accessible names alongside visual stars.

## Profile and media data

Use global Discord display name/avatar from bounded cached user fetches, falling back to stored username and initials. Do not require author to be in the viewed server for their profile, fetch bios, enumerate mutual guilds or use server nickname as global identity. Fetch identity only after visibility checks; hidden/unknown profile returns the same generic 404 with no name/avatar. An existing visible reviewer with no eligible items for a filter gets an empty state, not a missing-profile error.

Media enrichment uses existing service dispatchers and bounded deduplicated requests, cached by type/mediaId (initial TTL one hour, subject to provider requirements). If a provider is unavailable, show cached data or a title placeholder such as 'Movie · 12345'; preserve the review and score. Do not block an entire page on one provider. The launch title backfill is rate-limited and resumable; do not fetch metadata for every review on every page. Unfiltered review reads must not depend on media provider availability. Launch search uses retained names rather than provider search per keystroke; no TTL deletes the only searchable title. Provider-first is not the selected search design. Artwork/year display caching remains separate and can be a small in-memory cache; MediaTitle need only store names. Verify provider attribution, artwork and cache requirements before public release; do not presume existing Discord embed use establishes web presentation rights.

## Routes, ordering and paging

Canonical links: `/u/:discordUserId`, `/g/:guildId`. IDs are stable public identifiers, not authentication secrets. Anonymous links imply public access, not secret-link privacy. No global discovery or sitemap; recommend `noindex,nofollow` on pages and `X-Robots-Tag` on API responses (reduces indexing, not access control). Use generic link previews without review bodies.

The launch API includes q and title-metadata cursor versioning for database-backed title search.

| GET endpoint | Result |
| --- | --- |
| `/api/v1/users/:id/reviews?type=all&q=&limit=10&cursor=…` | Visible profile summary plus flattened global review cards, ordered by createdAt descending. |
| `/api/v1/guilds/:id/titles?type=all&q=&limit=10&cursor=…` | Server summary, membership freshness, title groups ordered by newest eligible review creation time; first three reviews per group plus review cursor. |
| `/api/v1/guilds/:id/titles/:type/:mediaId/reviews?limit=20&cursor=…` | All eligible reviews for one title, progressively loaded. Same visibility/membership policy as group list. |

All responses use `{items,nextCursor}` with route-specific profile/guild metadata; group entries contain `{type,mediaId,media,latestReviewCreatedAt,visibleReviewCount,averageScore,reviews,nextReviewCursor}`. No mutation API. No arbitrary author search endpoint. Default 10 title groups/profile reviews per page (a proposed tuning default within the user’s suggested 5–10, not a confirmed exact count), max 20; per-title expansion defaults to 20, max 50 reviews. Validate IDs, type enum, normalized q (maximum 100 Unicode characters), cursor size/version and limit. 400 malformed input/cursor, generic 404 inaccessible profile/guild, 409 stale cursor needing refresh, 429 bounded rate limit with retry guidance, 503 database/visibility/membership unavailable. Omit global totals in MVP to avoid extra aggregation; a title's review count and average include its full currently eligible member-review set under the page’s asOf creation cutoff, not merely the preview or loaded expansion page.

User-confirmed order: edits keep the original position. Title sort `(max eligible createdAt DESC, type ASC, mediaId ASC)`; reviews `(createdAt DESC, type ASC, id DESC)`. Profile uses the latter across all four collections; per-title expansion uses the same creation-time order. The displayed sort label is 'Newest reviews first'. Title-header recency is not displayed; latestReviewCreatedAt still determines ordering and remains an API field. Individual creation/edit dates stay visible. An edit to any member review must not move that review or its title group. New reviews and changes to eligibility/deletion can legitimately change positions. An excluded author's creation or edit must not influence group order.

Keep the original creation date visible and show 'Edited · [date/time]' when updatedAt is known. Provide a full timestamp (including timezone) in accessible text/help when the compact display uses a date. Compare normalized meaningful content before saving; update content and updatedAt atomically only when it changes, while preserving createdAt and originGuildId. A second actual edit replaces the prior edit timestamp. Changing a review into a quote/co-sign is an edit when its content changes; a new review starts with createdAt and no edit marker. No-op re-submissions retain any existing edit timestamp. Avoid a generic automatic ORM updatedAt hook that would mark administrative metadata updates as content edits. Legacy unknown timestamps stay null/missing until an observed edit occurs; no badge for unknown history does not assert that the review was never edited.

Use database aggregation to normalize/union four collections, filter visibility/current authors, then group/sort/limit. Do not read every review into application memory on every request. Prototype Prisma Mongo aggregateRaw and Mongo union/lookup pipelines against the pinned connector on disposable Mongo, with explicit BSON date/ObjectId handling. For four independent profile queries, keyset-query each collection to limit+1 and merge deterministically; server title aggregation needs globally correct grouping before pagination. Evaluate indexes on userId/createdAt/id and mediaId/userId only after explain against representative fixtures. Sort directly on stored createdAt; do not introduce activityAt or backfill updatedAt from createdAt. No edit-time index is required for this browsing flow.

Opaque, integrity-protected cursors bind route, media filter, normalized title query, title-metadata generation when searching, createdAt sort tuple, asOf creation cutoff, membership generation and relevant eligibility/deletion generation. A process-local generation counter rejects cursor reuse after deletions, privacy/opt-out or membership changes; instance identity invalidates cursors on restart. Relevant writers notify it. Content-only edits do not change sort tuples, advance this generation or invalidate a cursor: later pages may show the latest text/edit note in its original position. Fresh policy checks still apply on every page. Return 409 and invite refresh for invalidated membership/visibility/deletion state rather than silently skipping changed groups. New reviews after asOf wait for refresh; apply that creation cutoff before grouping so a new review cannot move an existing title between pages. Do not claim the displayed content is a transactionally frozen historical snapshot.

## Launch title search: selected design and alternatives

User confirmed database-backed title search for launch and a small backfill. Repository recheck found no persisted titles or media lookup: the Prisma schema contains RPS and four review models, and SearchResult.title is a transient service response. The unmerged Redis caching branch is not a reliable title inventory: entries expire, depend on prior access and were not verified deployed. Reusing those caches alone would silently omit reviews. Reuse existing provider clients and post-save detail responses, while adding the minimal MediaTitle collection below. Provider-first and per-review fields remain documented alternatives, not open launch decisions. No live database count or provider latency/access was measured.

### A. Provider search → returned IDs → eligible database reviews

This can reuse the existing authenticated clients, then query each review collection by its media IDs plus the unchanged user visibility/current-member policy. It needs no database schema change. One selected category adds one provider request before a DB query; All adds four provider requests (TMDB movie and TV separately, IGDB, Spotify album). They can run concurrently, but the slowest result gates a complete merged page. Token refresh and retry add hops; uncached title/artwork detail retrieval may add further requests. No millisecond estimate is defensible without measuring these credentials. Public search traffic shares rate budgets with Discord bot commands.

| Provider / repository evidence | Limits and consequences |
| --- | --- |
| TMDB: `src/services/MovieService.ts:14,42` calls movie/TV search with query only, then slices the first five results. No page argument or paging metadata returned. | Official [movie](https://developer.themoviedb.org/reference/search-movie) and [TV](https://developer.themoviedb.org/reference/search-tv) endpoints support page (default 1), language and adult filters. Movie search includes alternate/translated titles. Returning five loses reviewed matches even on page one. App code needs a paged search result wrapper if completeness matters; locale/adult choices can still omit existing reviewed IDs. |
| IGDB: `src/services/GameService.ts:39,99` interpolates search text, forces limit 5 and game_type (0,4,8,10), version_parent=null. | [Official IGDB docs](https://api-docs.igdb.com/) allow limit/offset, up to 500 per request; rate limit is four requests/second and eight open requests. Existing filters omit DLC/remasters/editions even if older reviews reference them. Web reuse needs safe query escaping, explicit filter semantics and paging/status handling; raising five alone does not fix omissions. |
| Spotify: `src/services/MusicService.ts:50` uses album search, limit 5, no offset/market, app client credentials. | [Current search reference](https://developer.spotify.com/documentation/web-api/reference/search) documents limit up to 10, offset up to 1000 and market availability constraints. The current client supplies no user-country context or market. App quota/access must be checked rather than assuming the historical client still works for every album. Different album editions have different IDs, so a popular edition may not be the reviewed one. |

Spotify [rate limits](https://developer.spotify.com/documentation/web-api/concepts/rate-limits) depend on app quota mode over a rolling 30-second window; handle 429/Retry-After. TMDB documents [changeable upper limits and 429 handling](https://developer.themoviedb.org/docs/rate-limiting); do not treat old per-10-second limits as current. Existing Service.search returns only SearchResult[], with no total/next/status/partial coverage contract. Existing public-query policy must still filter matches before counts/serialization; never return raw provider candidates as evidence of member reviews.

The core problem is correctness, not just an extra hop: provider search ranks its catalog, not this server’s reviews. A reviewed title can lie beyond a capped page, disappear from a provider/market, or be a different edition. A zero eligible match therefore cannot truthfully mean no matching reviews. Incrementally fetching provider pages also cannot guarantee the globally newest-created matching title comes first: a newer reviewed title may arrive from a later provider page. A bounded candidate set could be snapshotted and creation-sorted, labeled partial, but requires separate provider cursors/candidate snapshots and clear incomplete-search copy. Exhaustively paging the catalog before rendering is slow, rate-limited and still not a semantic guarantee. **Recommendation: do not use provider-first as the default complete review search.** It is acceptable only if the user explicitly chooses best-effort provider-ranked candidate lookup and accepts omissions; not a silent approximation to the requested review search.

Incremental change surface for A: new provider-search coordinator; pagination-capable methods in three service classes while preserving existing slash-command defaults; query escaping/market configuration/error/rate handling; additions to planned routes/query/cursor/UI modules and fixtures. No schema/backfill, but approximately 9–13 touched/new files for a bounded partial version. Making it exhaustive/stably paginated is larger and not recommended for this small v1. Counts are design estimates, not completed changes or time promises.

### B. Backfill reviewed title names and retain them going forward

**Selected smallest sound launch design:** a tiny separate `MediaTitle` collection with `(type, mediaId, title, normalizedTitle, fetchedAt)` and one unique `(type,mediaId)` index. This is an additive lookup, not a database redesign or review migration. There is no existing shared title lookup in the checkout; reuse existing services, not an imagined metadata service. Names are descriptive metadata, not review history. Do not update review.updatedAt when title names are refreshed.

Both current writing paths already fetch details after saving the review: `src/commands/reviews/utils/index.ts:327` onward and `utils/saveSharedReview.ts:88` onward. Upsert the returned title there; keep review save independent of title lookup failure and report pending coverage rather than losing a review. Co-sign and quote writes funnel through the latter. Existing getById/getSeriesById methods cover all four media types. For title-only backfill, their rich parsers need small guards: GameService assumes cover/release-date fields, MovieService series reads episode_run_time[0], and MusicService assumes images[0]/artists[0]. Prefer a minimal title-by-ID adapter or safe title extraction when unrelated artwork is missing, so a known title is not lost because its cover is absent.

One script enumerates distinct `(type,mediaId)` keys from the four active collections, computes missing lookup keys, and fetches each once. Dry run reports distinct count by media and proposed lookups without database writes; apply/resume upserts successful names and records failures for a later rerun. Never query the provider once per duplicated review. Reuse valid already-fetched titles if available, but do not assume a Redis branch was deployed. Backfill performs about U provider detail calls and U lookup upserts for U uncached distinct reviewed titles, versus R per-review field writes for R reviews. For illustration only, 100 unique titles means about 100 initial detail calls, not a measured production count. Start conservatively (e.g. one detail call per second, honoring provider backoff); rerun only unresolved keys. No job platform, title-version history, search engine or automatic broad catalog crawler.

Normalized literal substring search is deterministic over stored names and works during a provider outage after backfill. It does not automatically match provider aliases/translations; this is a clear title-name search contract. A substring regex generally will not benefit from a normal B-tree title index, so do not promise it will. The initial compound unique key supports dedup/upsert and type restriction; scan the small eligible title set with escaped normalized matching, then filter/group/order eligible reviews in Mongo. Measure lookup count/query timing on a read-only audit before adding indexes. At materially larger measured scale, reassess prefix/token search indexing as a separate performance change; do not preemptively add Atlas Search or another service. The present small lookup and compound key remain suitable without a database redesign.

Per-review alternative: add nullable title/titleNormalized to each of the four review models and backfill R documents, deduplicating provider calls by U IDs. It avoids a lookup join and may be equally small at the user-described scale, but duplicates names per reviewer, needs all ordinary/shared write paths to keep fields consistent, fans out renames and mixes metadata changes into review write handling. It is not wrong; prefer the tiny lookup because it leaves review documents untouched and naturally shares one name per media item. Do not add both approaches.

Concrete incremental package for B: schema (one model/index); new `src/reviews/mediaTitles.ts` helper; new `scripts/backfill-review-titles.ts`; two existing writer files for post-fetch upserts; small title-only parser guards in up to three service files if fixtures prove necessary; search additions in already-planned publicQueries/routes/cursors/browser modules; focused helper/backfill/query/UI tests and one operational README paragraph. Extra ongoing cost is one small idempotent lookup upsert per successful metadata fetch, with no extra provider request in the normal two writer paths.

## Archive storage proposal

Use one separate MongoDB collection, `ReviewMigrationArchive`, in the existing database. It is internal recovery data, not another set of public reviews. This needs no new service or user-facing archive UI. Scope is modest because it contains displaced duplicate documents plus before-images of canonical documents changed by migration, not every future edit.

Suggested fields (a future Prisma model may describe the envelope):

| Field | Purpose |
| --- | --- |
| id (ObjectId) | Archive document identity. |
| migrationBatchId (String) | Stable ID supplied to audit, apply, verification and rollback; reused when resuming. |
| recordKind (String enum) | `DUPLICATE` or `CANONICAL_BEFORE_IMAGE`. |
| sourceCollection (String enum) | Exact MovieReview, SeriesReview, GameReview or MusicReview collection. |
| originalReviewId (String) | Original Mongo ObjectId encoded as hex; source identity preserved inside payload too. |
| canonicalReviewId (String) | Retained review ID, interpreted with sourceCollection (not a cross-type ambiguous ID). |
| userId, mediaId (String) | Internal audit lookup; never returned by public endpoints. |
| originalDocumentEjson (String) | Full original document serialized in canonical MongoDB Extended JSON, preserving BSON ObjectIds, dates, missing fields and any fields omitted from the Prisma schema. |
| sourceChecksum (String) | SHA-256 of deterministic canonical EJSON for integrity/precondition verification. |
| archivedAt (DateTime) | Archive insertion timestamp, independent of review creation/edit timestamps. |
| operationState, restoredAt? | `ARCHIVED`, `APPLIED`, `RESTORED`; diagnostic checkpoint, reconciled against actual source state after interruption. |

Unique index `(migrationBatchId,sourceCollection,originalReviewId,recordKind)` makes same-batch retry an upsert with checksum equality required, never an overwrite with changed source data. A restricted JSON manifest file, keyed by migrationBatchId, holds the plan checksum, baseline counts, winner map, status and verification results; no second database collection or migration dashboard is necessary for the current scale. Keep this manifest with the backup; normal logs need only IDs/counts. Archive collection has no TTL and no automatic purge; agree retention before production migration.

Read raw source documents through a version-compatible MongoDB driver so no unknown fields disappear through Prisma projection. This dependency belongs only to migration tooling. First write and verify the archive payload, then compare the unchanged source checksum and delete the duplicate; a crash between these stages safely resumes by examining both collections. Never delete if archive write/checksum verification failed. Writers are paused for apply; conditional writes/transactions where supported further protect preconditions. Verify the largest documents fit MongoDB's document-size limit after EJSON encoding before apply; an oversized payload blocks that record rather than truncating it.

Rollback uses the saved original `_id` and exact payload, not newly generated review IDs. Restore a missing document; if its ID already exists, require a checksum match or flag a conflict. Restore canonical before-images only if the current record still matches the expected post-migration checksum; export/reconcile any later edits instead of overwriting them. Drop incompatible global unique indexes under controlled maintenance before restoring duplicates and reinstate the appropriate guild-era indexes. Preferences are never restored from this archive or reset. A dry run emits a planned archive/keep/delete manifest without inserting archive rows; apply, verify and rollback are separate explicit modes, defaulting to dry run.

Public review aggregation must enumerate only the four active review collections. No lookup/union or metadata enrichment targets the archive; archive payloads do not appear in counts, profiles, search, title ordering or backups shared with browser clients. Same database does not mean publicly queryable: only the three allowlisted read routes exist.

## Safe migration, backfill and rollback

MongoDB with this project's Prisma v6 uses schema synchronization rather than Prisma Migrate; see [Prisma v6 MongoDB connector](https://www.prisma.io/docs/orm/v6/overview/databases/mongodb). Optional fields and missing-vs-null filtering need explicit handling; defaults do not prove persisted historical values were backfilled.

1. Reconcile remote master/autocomplete and global branch in a future implementation branch; inspect deployed image/schema/data independently before assuming legacy shape. Confirm operator access, backup/restore procedure and target DB name without logging credentials.
2. Build a read-only, batched, deterministic migration audit. Inventory per-collection counts, duplicate groups, differing score/comment/private values, missing dates/flags/guilds; emit a private artifact with migration ID and source checksums. No destructive default mode.
3. On a disposable restored database, archive full duplicate documents (including IDs and every field) plus winner mapping/checksums; test restore before deletion. Keep the newest created record only after the conflict report is approved. If any duplicate has explicit private restriction, preserve that restriction conservatively on canonical selection pending resolution; never convert it to public by accident.
4. Stage additive schema/client changes without the global unique indexes. Keep new fields optional until backfill is proven. Stop/drain review writers for final audit/apply; old guild-scoped writers must not run against the deduplicated global store.
5. Backfill origin only from verified evidence, preserve createdAt, normalize isPrivate where legacy-public status is established, and leave unknown legacy updatedAt null/missing. Creation time alone determines order; neither creation nor migration time is an edit-time backfill. Persist a resumable checkpoint and full rollback manifest. Do not set historical timestamps to deployment time. Preference absence remains public.
6. Archive/checksum first, then apply deletions in bounded batches with verified preconditions. Reruns must skip already-completed operations and detect source changes. Validate counts and distinct user/media cardinality before applying unique indexes; regenerate client and deploy global-aware writers together.
7. Validate all ordinary, button, modal, co-sign, quote and delete paths; replace findFirst/create race with unique-key upsert or conflict handling. Verify privacy inheritance/guards, no unwanted reset of isPrivate on score-only/shared writes, origin immutability and timestamps.
8. Keep web routes disabled until policy/membership tests pass and HTTPS/intent readiness is confirmed. Enable in a test guild with fixture accounts, then register public commands and enable web routes as an explicit later rollout.

Rollback: web-only rollback disables WEB_ENABLED/links while retaining preferences. Global-storage rollback is a separate data recovery procedure: pause writers, retain/export all post-migration writes and preferences, remove incompatible unique constraints only under operator control, restore archived originals and reconcile new writes, deploy matching old writers, verify counts before resuming. Restoring an old snapshot over live writes loses data; do not call it a safe rollback. Preserve opt-outs even if the web code is rolled back. Archive retention/removal follows an explicitly approved operational retention decision.

## Acceptance scenarios

- A member reviews a movie in server B; their profile and server A library include it, and A shows Reviewed in another server. A same-server origin is unmarked; unknown origin is unmarked.
- A nonmember's review never appears in server A even if created in A. Rejoining includes their eligible global reviews again.
- Opting out hides all old/new reviews, profile metadata, member counts/activity and copied source content from public routes; direct API URLs and expansion cannot bypass it. Unhiding restores non-private records. Discord posts remain as they were.
- New public users require no setting step. Explicitly private reviews never appear anonymously, including in the origin server's web library.
- Same provider ID across Movie/TV is distinct. Scores retain the 1–5 scale; missing optional metadata never becomes invented data.
- Editing an older review updates its content and Edited timestamp but preserves its position on profiles and within title groups; editing any review never moves its title group. Title groups use the latest createdAt among eligible current-member reviews. New reviews can move groups; paginated expansion returns all eligible reviews in creation order.
- Fixtures include an older game review edited after a newer movie review: the game and its group stay below the movie. A second meaningful edit updates the edit note; a no-op save, identity refresh or visibility toggle does not. Missing legacy updatedAt remains unknown with no fabricated timestamp; the first observed edit adds the note without changing createdAt. Content-only edits between page loads neither duplicate/skip records nor expire creation-time cursors.
- No viewer login, no web content mutations, no membership directory; command-generated links work in both normal and Discord in-app browsers.
- Title search and category filters combine on the same screen across all eligible records, including unloaded titles. Automatic loading begins with the proposed 10-item batch, deduplicates, stops at end and recovers from errors; no routine Load older control. Query/filter changes reset cursors and ignore late responses. Incomplete title metadata is labeled, not silently reported as no matches.
- Broken provider, stale membership, database failure, malformed cursor and deleted/hidden profile each have a useful, nonleaking response.
